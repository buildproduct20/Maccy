# Clipboard capture, restoration, formats, privacy

## Required behavior and native boundary
`NSPasteboard.general.changeCount` is the macOS change signal; poll ~500ms initially, adjustable internally, and use a bounded queue. Read the changed item on a permitted thread immediately enough to avoid races; if changeCount changes during a multi-format read, retry once or drop with a diagnostic **without** logging content. Do not hold multi-MB buffers through multiple parallel background tasks. The native `objc2-app-kit` path is preferred if an interoperability test proves correctness; a minimal Swift AppKit adapter is acceptable as a measured fallback.

When the user clicks a history row: restore the *appropriate pasteboard representations*, update copied timestamp/recency without duplicating the item, close the popup. **Do not** send an OS keyboard event, Cmd+V, Accessibility request, or event tap. The user will paste manually.

## Format requirements
| Kind | Capture | Persistence | Restore |
|---|---|---|---|
| Plain text | `public.utf8-plain-text`/NSPasteboard string, preserving Unicode/newlines | Bounded searchable text and full text on disk | text representation |
| Rich text | Text with HTML/RTF where offered | Format-tagged RTF/HTML bytes plus readable text fallback | Correct pasteboard type for each retained format, not plain text only |
| Image | PNG/TIFF/JPEG/HEIC or native image pasteboard representation | Original bytes or provably lossless/reversible representation, content-addressed in application private folder | Compatible image representations; avoid accidental lossy re-encoding |
| Files | `NSPasteboard.PasteboardType.fileURL` across multiple pasteboard items | Ordered URL representations only, **not file content** | Multiple pasteboard items preserving source references where possible |

Multiple types can coexist in a single copy. Model a `ClipboardRecord` with *one display kind* plus `Vec<ClipboardRepresentation { pasteboard_type, blob_ref_or_inline_bytes }>` so text fallback and rich or image formats are not lost. Do not classify HTML or RTF as an unrelated duplicate when the plain text matches but formats matter.

Model content types as actual UTI strings and avoid brittle platform guessed aliases. Validate file URL serialization against macOS pasteboard readers. Do not dereference paths on capture, avoid security-scoped bookmark data for an unnecessary personal lightweight app.

## Deduplication semantics
Use stable fingerprint of canonical, nontransient representations, e.g. BLAKE3 over length-delimited sorted `(UTI, bytes)` pairs (not nondeterministic dictionary iteration). Preserve ordered file URLs where ordering matters. Two exact-equivalent copies -> one row; refresh `last_copied_at` and increment `copy_count`. If same textual fallback but richer formatting arrives, do not strip richness: either merge representations only when proven equivalent or preserve a distinct item. Avoid hash-equality-only decisions for security-critical correctness; collision risk negligible but verify the canonical representation matches if there is ambiguity. Existing Maccy uses semantic supersession across `HistoryItemContent`; preserve important supported behavior, not its SwiftData internals.

A write-back from Maccy Lite must not create an additional row. Guard using pasteboard change generation plus bounded self-write intent. The user's re-selection is allowed to refresh recency; do not permanently blacklist matching content from other apps.

## Sensitive content
Respect and test pasteboard types for concealed/transient/autogenerated content, password manager markers, original Maccy exclusion filters, excluded apps, excluded pasteboard types and regex patterns. Check exclusions **before** disk persistence, thumbnail generation, preview logging or sending events. Keep a conservative optional detector for high-confidence credentials and PEM keys as defense in depth; never claim universal secret detection or use cloud detection. Avoid storing unrecognized app-private/drag-only pasteboard blobs; allowlist supported types.

Logs only show operation IDs, types, sizes, timings and sanitized error codes. No text, clipboard raw bytes, image contents, personal file paths or secrets. Production app has no analytics, telemetry, server, auto-update or network uploads.

## Image memory safety
Hard-limit input sizes and decoded pixel dimensions using documented settings; large/unsupported items should be skipped with a nondisclosing status or handled with bounded disk-backed flow, never cause repeated OOM. Decode thumbnails lazily and cache by bytes with eviction (example starting budget 8 MiB, adjust by measurement). Avoid decoded full-size image retained by model objects. Prefer direct data transfer for original image when valid; no HEIC lossy transcode by default. Measure all helper process memory if used.

## Privacy failure-mode matrix
- Excluded application/type: no item, no persistence, no preview, no content logging.
- Missing/corrupt blob: fail gracefully, show safe error, do not paste corrupted data.
- SQLite write error: keep clipboard content unchanged, report failure internally, do not evict old rows until successful commit.
- App crash between content write and DB commit: unreferenced staged file is cleaned on next startup.
- Privacy rules changed: future captures respect new rules; optional explicit manual purge; avoid silently rewriting old content.
- Original Maccy concurrently running: each app may observe clipboard changes; ensure self-write loop prevention and do not modify original application's storage.
- Quit: no hidden clipboard-clearing operation; no additional background process/service left running.

## Concrete tests
`C01` unicode/plain, `C02` CRLF/newlines, `C03` HTML+text, `C04` RTF+text, `C05` PNG/screenshot, `C06` TIFF/native conversion, `C07` multiple file URLs, `C08` self-write loop, `C09` cross-copy stale changeCount, `C10` transient/concealed, `C11` ignored application/type/regex, `C12` oversize, `C13` corrupted blob, `C14` same text richer format, `C15` no synthetic paste/no Accessibility prompt.

Use named/disposable pasteboards where API permits, and isolated macOS test runner for real general-pasteboard tests. Do not touch real user clipboard in normal unit tests.
